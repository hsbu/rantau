## B-01 design for shared-interface agreement

Prepared 2026-10-17 following the request to begin Dev B work; the requester approved this interface/storage design on 2026-10-17. The task checkbox records implementation and required checks separately from review/merge. The existing public `ActorContext`, money, approval and payment contracts remain unchanged.

**Approach:** use opaque server sessions backed by PostgreSQL. This fits the existing cookie-only chat relay and permits immediate logout/revocation and consent checks. Signed self-contained tokens would require an additional revocation mechanism; process-local sessions would lose authority state on restart and are unsuitable for integrated use. B-01 integration tests use isolated PostgreSQL; no fake authentication is connected to the application.

**Identity and credentials:** provision synthetic student and sponsor identities through an explicit isolated-demo bootstrap command; do not expose registration, caller-selected roles or default passwords. Credentials come from ignored local configuration, are salted/hashed before storage, and never enter logs, responses or model context. Login verifies credentials and issues a fresh cryptographically random token. Store only its digest. Resolve actor ID, tenant, role and scopes from current trusted records on every authenticated request; reject inactive actors, revoked sessions and expired sessions. Session lifetime: one hour, independent of financial approval expiry.

**Approved additive HTTP interfaces:**

| Method / path | Request and result | Enforcement |
|---|---|---|
| `POST /api/v1/auth/login` | Strict `{username, password}`; return `{authenticated: true, role}` and a session cookie. | Generic credential failure; bounded input; trusted-origin check and bounded login attempts. Never accept actor, tenant, scopes or role in the request. |
| `GET /api/v1/auth/session` | Return `{authenticated: true, role}` after verifying the cookie. | No raw token, credential digest, session ID or private account data in JSON. |
| `POST /api/v1/auth/logout` | Empty body; revoke the current session and clear its cookie. | Trusted-origin check; no financial mutation. |
| `PUT /api/v1/student/sharing-consents/{sponsor_id}` | Strict `{allowed_shared_fields, expires_at}`; return the saved sharing summary without credentials/session data. | Verified student grants only their own data to an existing same-tenant sponsor. Agreed fields: `tuition_summary`, `payment_summary`, `case_summary`; cannot grant payment authority. |
| `DELETE /api/v1/student/sharing-consents/{sponsor_id}` | Revoke the student's grant; return 204. | Verified student and trusted-origin check; subsequent sponsor reads must observe revocation. |

The session cookie is host-only, `HttpOnly`, `SameSite=Strict`, `Path=/`, with `Secure` required outside explicit local development. State-changing routes validate a configured trusted frontend origin; do not trust forwarded identity/host claims. Missing trusted configuration/storage remains a sanitized 503; invalid credentials/sessions return a generic 401; unauthorized resource reads return a non-disclosing 404. Financial/approval endpoints remain outside this ticket.

**Storage and ownership agreement:** the requester-approved `migrations/001_auth.sql` adds shared `actors`, `auth_credentials`, `auth_sessions`, `student_sponsor_consents` and internal hashed login-attempt counters. Actors and sharing grants use UUID primary keys; tenant-bound fixture aliases remain unique and match `ActorContext`. Sessions store unique token digests, credential versions, expiry and revocation. Bootstrap is explicit, restricted to the isolated demo tenant and refuses production or overwriting an existing tenant; no startup seeding/table creation occurs. Dev C's later migrations/reset must preserve the agreed alias/foreign-key relationships and session-revocation boundary.

**Access and integration:** `backend/authz/` supplies session verification plus reusable tenant, ownership, sponsor-role and field-specific sharing checks. Students cannot enter sponsor decision paths; sponsors may read consented student summaries but never acquire authority over student-owned funds. Approved shared integration updates `backend/dependencies.py` and `backend/main.py`, exports agreed HTTP shapes through the existing contract generator, and documents sanitized configuration in `.env.example`/README. `/ready` continues reporting unavailable domain services until A/C wiring exists. Dev A consumes verified sessions; Dev C enforces the access checks on every domain read and the later B-02 gate inside execution transactions.

**Validation required:** write and observe failing tests before product code. Cover separate credentials/sessions, forged identity headers/body/chat, token tampering/fixation, expiry/logout/revocation, disabled actors, tenant isolation, sponsor-role restrictions, missing/expired/revoked/field-limited consent, cross-tenant grants, origin checks, login-attempt limits and sanitized errors. Exercise an isolated PostgreSQL database for persistence/restart and immediate consent revocation. Run the complete backend suite, strict mypy, Ruff, contract generation/typecheck where shared HTTP models change, diff checks and index hygiene. Keep credentials, tokens, DB data and generated output ignored. Record actual commands/results here; do not label B-01 complete using test-only repositories.

## B-02 approved design for shared-interface agreement

Prepared 2026-10-17 for the request to continue to the next ticket; the requester approved implementation on 2026-10-17 ("okay do the work then"). Scope follows MVP sections 3–4 and roadmap B-02: deterministic decisions against trusted simulated financial state. B-03 owns approval/mandate creation and consumption; C-03 owns ledger changes and reservations. Existing HTTP endpoints, `ActionIntent`, `PolicyDecision`, money units, decision/reason enums and `AuthorizationPort.evaluate(actor, action)` stay unchanged.

**Recommended approach:** implement a pure policy evaluator plus a transaction-bound authorization adapter in `backend/authz/`. A pure function alone is easy to test but cannot guarantee fresh identity/state or a durable audit; implementing C's financial tables inside B-02 would cross ownership and expand scope. The adapter keeps the established port while requiring an injected trusted repository and the caller's PostgreSQL connection. It never accepts financial facts from a request body, chat, document or model output.

**Trusted adapter interface:** propose B-owned internal typed models in `backend/authz/policy_models.py` and `PolicyRepository` in `backend/authz/policy_repository.py`, consumed by Dev C. `load_payment(connection, actor, action)` returns an immutable snapshot or a scoped unavailable error; `load_reconciliation(connection, actor, action)` returns submission scope only. Both must use the supplied transaction and tenant-scoped queries, locking mutable authority/financial rows for execution. No process-local implementation is wired into the application. Test repositories live under `tests/`.

| Snapshot | Required trusted facts |
|---|---|
| Payment resource | Tenant, current immutable `PaymentIntent`/`PaymentTerms`, requester, source-account owner/currency/active state, authenticated resource-access relationship. IDs and `action.terms_hash` must match the current stored revision; a caller-provided hash is never proof of authority. |
| Beneficiary and quote | Tenant-scoped registry identity, verified status/current fingerprint, permitted purpose/recipient relationship; stored `FxQuote` including amounts, currencies, fees and expiry. Match every quoted term against the current intent. |
| Current policy | Active version, permitted purposes/currencies, configured routine threshold, hard account caps and source-account IANA timezone. No product threshold is invented in code. Tuition also requires a current usable `UniversityPolicy` for the obligation and institution. |
| Spending | Available account balance after existing reservations; completed spending plus outstanding reservations for the relevant day/month and proposed transfer's existing reservation, if any. Repository identifies reservation ownership so rechecks neither double-count nor subtract unrelated reservations. Period boundaries use account timezone and aware UTC timestamps. |
| Authority and risk | Current account-owner mandate (owner, delegate, account, beneficiary, purpose/currency, limits, validity/revocation), stored authenticated `Approval` with all immutable terms, active holds and trusted risk floor. Sharing consent and advisory low-risk scores supply no debit authority. |
| Reconciliation | Tenant, case/payment/obligation relationship and authenticated student's right to submit evidence; never permission to approve a case or post university credit. |

**Decision rules and precedence:** reject invalid current sessions, cross-tenant/resource access and missing action scope before exposing resource facts. Preserve T0 reads through B-01's existing scoped guards; do not invent a read action in `ActionIntent`. For state-changing actions, deny fundamentally unauthorized operations with existing reason codes. Recheck transfer state before any possible `ALLOW`: `PROCESSING`/`DELIVERED` cannot resubmit and `OUTCOME_UNKNOWN` requires status reconciliation; terminal rejected/cancelled/expired/failed intents cannot execute again. Only `DRAFT`, `AWAITING_APPROVAL` and `AUTHORIZED` are candidates, subject to every remaining check.

An active hold, unverified/mismatched beneficiary or T3 risk floor yields `HOLD` at T3. Expired quotes, insufficient available balance, hard account-limit breaches and unusable institution policy cannot yield `ALLOW`, even with an approval. Non-ALLOW results use the existing specific reason code (`QUOTE_EXPIRED`, `INSUFFICIENT_FUNDS`, `LIMIT_EXCEEDED`, `UNIVERSITY_POLICY_UNKNOWN`, etc.); unknown/missing trusted configuration fails closed through `ServiceUnavailable`, never a permissive default. Exact error/decision mappings are covered by table-driven tests. For `CREATE_INTENT`, C stages a scoped immutable draft in the same transaction before evaluation; `REQUIRE_APPROVAL` permits retaining an awaiting-approval proposal, never debiting. `HOLD` permits only retaining a held proposal. These are readiness decisions; `EXECUTE_PAYMENT` always reloads and reevaluates. `DENY` cannot create an authorized intent.

T1 is available only for an eligible allowance under a current funding-owner mandate, verified recipient and cumulative limits including reservations. Tuition, a missing/ineligible mandate, changed terms, amounts outside routine eligibility or a T2 risk floor require T2 exact funding-owner approval; an explicit approval does not waive hard account caps or holds. Compare every `PaymentTerms` field, not only its hash, and require current `APPROVED`, unexpired, unconsumed owner authority. Students may self-confirm their own funds through B-03; sponsors cannot approve student-owned funds. Return `REQUIRE_APPROVAL` when fresh owner consent is needed, with expiry/terms-mismatch reasons where applicable. Effective tier is the maximum of deterministic policy and trusted risk floor. Reconciliation approval/ledger mutation is always outside this gate's submission permission.

**Action scopes proposed for agreement:** retain `payment:propose` for creating an intent; add explicit `payment:execute` and `reconciliation:submit` grants to the synthetic student, and `payment:execute` to the synthetic sponsor. Sponsor approval still requires B-01's separate `sponsor:approve` and funding ownership. These grants permit entering the gate, not automatic payment approval. Existing sessions whose stored scopes differ must authenticate again; no role-only fallback or implicit grants for existing databases.

**Transaction and audit boundary:** `TransactionAuthorization(connection, auth_service, repository).evaluate(actor, action)` revalidates B-01 identity on that same connection, obtains fresh database time, loads the trusted snapshot, evaluates it and inserts a redacted decision before returning the existing `PolicyDecision`. It must reject autocommit use and never open/commit a second transaction. Propose shared migration `002_policy_audit.sql` for `policy_decisions`: UUID primary key/public audit alias, tenant/actor alias, action, resource alias, decision, tier, reason and database timestamp. Store no raw session token, account identifier, balance, document/chat text or full snapshot. B-06 later extends audit/hold workflows. If audit storage fails, no `ALLOW` is returned. The explicit migration runner must apply ordered checksummed migrations without changing the existing `001_auth` checksum.

Dev C invokes this adapter inside the transaction that locks account/intent/approval/mandate/hold state and atomically consumes authority, reserves limits, creates the transfer and debits. Preview decisions cannot be reused to execute later. Rejected attempts need their decision committed without a debit; exceptions/rollback must not be represented as a durable audit. C's executor must recheck after concurrent changes and keep idempotency/status-before-retry rules. B-02 will not claim that those unimplemented ledger effects have been verified.
