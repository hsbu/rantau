## Agreed foundation decisions and integration boundaries

- The requester approved the S-01/S-02/A-01 proposal on 2026-10-16 and confirmed the product name Rantau. This file consolidates the former foundation notes and implementation proposal; executable field definitions remain in `backend/contracts/`, with product requirements in the MVP/roadmap.

Quote rates are exact decimal strings in destination major units per source major unit, rounded half up to destination minor units; totals equal principal plus fee. Times are timezone-aware. `terms_hash` is an opaque trusted-service digest, never generated authority from the agent.

## A-03-F1 durable state and run-storage proposal

Prepared 2026-10-17 after the requester selected durable conversation memory and run diagnostics. This proposal uses the existing `ConversationStore`, `RunRepository`, B-01 sessions and C-01 PostgreSQL foundation. It does not expand memory to raw transcripts or introduce financial actions. The requester may provide team agreement as previously authorized; AGENTS.md section 3 requires agreement before shared schema/migration changes.

Approved for the team on 2026-10-17: requester selected "Approve and implement both adapters." This authorizes the additive schema, scoped storage/retention, safe run-retrieval behavior and atomic completion below; that design approval did not authorize publication. The requester separately authorized pushing/opening [PR #17](https://github.com/hsbu/rantau/pull/17) on 2026-10-17.

**Additive storage:** propose `migrations/020_agent_storage.sql`, with no edits to existing B/C migrations or tables. `agent_conversations` is keyed by `(tenant_id, actor_id, session_id, conversation_id)` and stores schema-versioned `ConversationState` JSON, an optimistic revision, scenario run number, update time and expiry. `agent_runs` stores immutable run ID, tenant/actor/session, optional conversation ID, scenario run number, requested intent, allowlisted tool-event/resource metadata and creation time. Run IDs are unique; repeated identical writes are idempotent and conflicting writes cannot overwrite history. Retained run records must not cascade-delete with sessions/credentials. A Dev A migration helper composes the existing B/C migration runner with the new migration explicitly; no automatic startup migration, seed or reset is added.

**Data boundary and retention:** keep only the current typed tuition draft, previous intent and option identifiers/counts; do not store raw user text, assistant prose, model output, account balances, full quotes, approvals, cached permissions, cookies or tokens. Proposal defaults: 30-minute idle draft expiry bounded by session expiry; 128 active drafts per tenant across workers; at most 64 KiB per state record. Expired drafts are lazily purged; a scenario reset invalidates the previous draft without modifying C's reset service. Run metadata is bounded to 64 tool events/resources and 32 KiB, append-only and retained without automatic deletion during the MVP; it is not the source of truth for financial/security effects. B-06/C audits remain authoritative for those effects.

**Current authority on every access:** reuse B's `AuthService.current_actor` in short transactions. Require the current verified student, `student:read` and an exact tenant/actor/session match when loading/saving drafts or retrieving runs; repeat the check before committing a completed turn. Expiry, logout, credential change, scope removal or actor disablement must prevent access/commit. A new login has a new namespace even for the same student; sponsors cannot read student runs through this API. Resource references/draft IDs remain server-side data, never authorization. Public HTTP request/response shapes and model context remain unchanged.

**Concurrency and atomic completion:** serialize a conversation across workers using a bounded PostgreSQL advisory lock and a revision check, with a five-second contention limit and sanitized unavailable response. Do not retain auth/financial row locks or an open database transaction across model/network calls. Atomically save the new typed state and its completed run metadata in one short transaction after revalidating the session; a failed/cancelled turn commits neither. Add the minimal internal graph/session completion hook needed for this guarantee; keep `RunRepository.put` idempotent for the existing router path. Missing/corrupt/oversized storage fails closed, with no silent process-local fallback in configured durable mode. Offline demos can explicitly retain their existing in-memory adapter.

**Run retrieval semantics:** the existing `GET /api/v1/agent/runs/{run_id}` continues returning `AgentResponse`, but durable retrieval reconstructs a fixed safe diagnostic message plus the saved requested action, events and resource references. It does not replay original assistant prose or restore a transcript; callers must recheck current resource state. Stored run metadata records past diagnostics, not current financial authority or proof of a debit/posting.

**Integration limit:** deliver real PostgreSQL adapters and an explicit trusted-services construction seam; do not wire test domain/auth adapters into HTTP or mark `/ready` healthy. C-02 domain reads and later A-04/A-05 protected actions remain independent dependencies. Correlation with later financial actions uses agreed server-owned run/scenario identifiers; no new financial port field is added unilaterally.

**Required evidence before completion:** observe failing tests first; verify persistence across adapter/process recreation, exact tenant/student/session/conversation isolation, expiry/logout/revocation/scope changes, lazy TTL/capacity cleanup, scenario reset, two-worker serialization/timeout, cancellation/rollback and atomic state/run writes. Assert PostgreSQL rows, immutable/idempotent runs, bounded/corrupt payload rejection and absence of raw text/secrets from stored JSON and retrieved messages. Exercise HTTP using real B-01 sessions with test-only domain/classifier adapters and verify that unwired application configuration still returns 503. Run the complete backend suite, strict typing, Ruff and repository hygiene. Keep implementation/review status separate; no migration or adapter implementation is claimed before approval.

Implementation notes, 2026-10-17: database operations and advisory-lock connections run through worker calls to support Windows' default event loop. Session checks are repeated after lock waits and before commit; an expiry-during-capacity-wait regression reproduced a failure before the final check was added. The final state/run transaction is cancellable before its commit decision; completed commits remain historical records if response delivery is later interrupted. `durable_agent_services` is explicit construction only; default HTTP wiring remains closed. B/C financial schemas, gate/executor behavior and public HTTP shapes are unchanged. Publication CI initially reported 476 passing tests and one pre-existing auth-server test failure because `.generated` did not exist with the CI-provided database. The test now uses pytest's temporary directory for subprocess logs; runtime authentication and the spoofed-address assertions are unchanged. The focused test passed locally; CI rerun is pending.
